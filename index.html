agentope

Offline evaluation of LLM agent decisions, from logs you already keep. No logprobs needed.

The question it answers: at one decision in my agent, if a different policy had made the choice, would outcomes have been better? And how far can I trust that answer?

A decision point is one place where the agent picks from a few options: which tool to call, which model to route to, which prompt to use. You give agentope the choices your agent made, the outcomes that followed (resolved tickets, purchases, ratings), and an alternative policy. It estimates the alternative's average outcome and reports how much evidence backs that estimate.

How it works

1 · DecisionsWhat was chosen, from which options, in what situation.
2 · OutcomesWhat happened afterwards, matched by a shared key.
3 · TargetThe alternative policy you want to test.
4 · ReportEstimate, interval, verdict and assumptions.

Under the hood it reweights logged decisions: those the target would also have made count more, the rest count less (inverse propensity scoring). That only works if it knows how likely each logged choice was, which is where evidence levels come in.

Evidence levels

LevelWhere the probabilities come fromTrustStatus
1 · LoggedRecorded when deciding, because the system randomized a little (explore / randomize).Strongestavailable
2 · SampledThe logging LLM is re-run on stored inputs and its choices are counted.Good, if inputs are completev0.3
3 · EstimatedModeled from the context you logged.Weak: assumes nothing important is missing from contextavailable
4 · ModeledNo probabilities; an outcome model only.Weakestv0.4

agentope picks the strongest level your data supports. Level 3 refuses to run until you explicitly accept its assumption.

Guide: your first evaluation

  1. Install

    From this repository:

    uv sync
uv run agentope --help

  2. Log decisions with a little exploration

    Wrap the decision. With probability ε (here 5%) it takes a random option from a list you consider safe, and records that it did. Those explored decisions give agentope exact probabilities.

    import agentope as ao

tool = ao.explore(
    "tool_choice",
    llm_choice=tool_name,                      # what the LLM picked
    safe_candidates=["search", "lookup_order", "__none__"],
    epsilon=0.05,
    context={"intent": intent, "tier": tier},  # what describes the situation
    join_key=conversation_id,                  # links to the outcome later
    log="decisions.jsonl",
)

    For decisions made in code (e.g. a model router), use ao.randomize(...) with explicit probabilities.

  3. Record outcomes

    One row per outcome, with the same join key and a timestamp (unix seconds or ISO 8601 with a timezone). Record failures too, as 0, or, if your system only ever records successes, pass --absent-means-default when evaluating.

    join_key,t,value
conv-8812,1763283600,1
conv-8813,1763283900,0

  4. Write the policy you want to test

    A function from the situation to probabilities over the options. Options you leave out get probability 0.

    # policy.py
def lookup_first(context, candidates):
    if context["intent"] == "refund":
        return {"lookup_order": 1.0}
    return {"search": 1.0}

  5. Run the evaluation

    --horizon is how long after a decision an outcome still counts.

    uv run agentope eval decisions.jsonl --decision-point tool_choice \
    --outcomes outcomes.csv --horizon 7d --target policy.py:lookup_first

  6. Read the report

    The headline is the difference: the target's estimated mean outcome minus what your agent actually achieved, with a 95% interval.

    Evidence level   L1 Logged (ε-exploration)
Logging policy   0.494  realized mean outcome (all 4,000 decisions)
Target policy    0.663  SNIPS   (IPS 0.634)
Difference      +0.169  95% CI [+0.068, +0.265]
Verdict          ok

Example: from a support agent's traces

A customer-support agent runs an open model (qwen2.5-7b-instruct on vLLM) and is traced with OpenTelemetry. For each conversation, the model decides whether to search the knowledge base, look up the order, escalate to a human, or answer directly. The helpdesk records whether each ticket was resolved. The team wants to know: should the agent always look up the order when the customer gives an order number?

The trace

One trace per conversation, exported from the OpenTelemetry Collector. Content capture is off, so there are no prompts and no message text, only span attributes. The agent's tool choice is wrapped in agentope.explore (ε = 0.2, never escalating at random), which records its coin flip as agentope.* attributes on the model span:

tool = ao.explore(
    "tool_choice", llm_choice=tool_name,
    safe_candidates=["search_kb", "lookup_order", "__none__"],
    candidates=["search_kb", "lookup_order", "escalate_to_human", "__none__"],
    epsilon=0.2, join_key=conversation_id,
    log=lambda record: span.set_attributes(ao.span_attributes(record)),
)

1 · Import the traces

Each chat span that starts a turn becomes a decision. The chosen action comes from the execute_tool span that follows it, or __none__ if no tool ran. Context comes from the attributes you name.

uv run agentope import --traces traces.otlp.json.gz --map tool \
    --context intent=app.intent,has_order_number=app.has_order_number,customer_tier=app.customer_tier \
    -o decisions.jsonl

3 · Describe the policy to test

# policies.py
def lookup_when_order_number(context, candidates):
    if context["has_order_number"]:
        return {"lookup_order": 1.0}
    return {"search_kb": 1.0}

def escalate_pro(context, candidates):
    if context["customer_tier"] == "pro":
        return {"escalate_to_human": 1.0}
    return lookup_when_order_number(context, candidates)

This estimate assumes:
  • Logged propensities are the probabilities actually used when deciding
  • Whether a decision was explored did not depend on its context
  • Which tool is called matters, not its arguments or wording (action map: tool)
  • Only tool_choice changes; later steps behave as they did under the logging policy
  • An outcome missing within 3d means outcome = 0

Steps 1 and 4 also run as one command: agentope eval --traces traces.otlp.json.gz --context … --outcomes helpdesk.csv --horizon 3d --target ….

Reading it: looking up the order whenever there is an order number would have resolved about 8.8 percentage points more tickets, and the interval stays clearly above zero. The estimate uses only the 1,012 explored conversations, but it is compared against how all 5,000 actually went.

5 · A policy the data can't judge

The second policy escalates every pro customer. Escalation was never explored (it isn't a safe candidate), so the logs say nothing about how a random escalation would have gone:

uv run agentope eval decisions.jsonl --outcomes helpdesk.csv --horizon 3d \
    --target policies.py:escalate_pro
Target policy    no trustworthy estimate
                 (SNIPS 0.702 · IPS 0.529 · difference +0.119, shown for diagnosis only)

Diagnostics      ESS 251 (25% of n) · max weight 3 · min propensity 0.333
                 support violations 24.6% of target mass (249 decisions)

Verdict          unreliable
                  • support violations carry 24.6% of target probability (limit 1%)

This is the tool doing its job: instead of a confident wrong number, it tells you what to log. Add escalate_to_human to safe_candidates for pro customers if random escalations are acceptable, or evaluate at Level 3 with --level 3 --accept-unverifiable. Level 3 uses all 5,000 conversations, but it rests on context capturing everything that drove the model's choice, and its verdict is at best weak.

What the verdict means

okEnough effective data and no red flags. Still read the listed assumptions.
weakA usable signal, but with caveats: Level 3, few effective samples, or many outcomes missing.
unreliableNo trustworthy estimate. The numbers are shown only for diagnosis, and the report says why.

When things go wrong

  • "refused": there are no logged probabilities, so it would need Level 3. Add --accept-unverifiable if you accept that context captures everything that mattered, or start logging with explore.
  • Support violations: the target picks options your logs never take (e.g. outside safe_candidates). Nothing in the data can say how those would have gone.
  • Low effective sample size: the target differs a lot from what was logged. Collect more explored decisions or raise ε.
  • Many expired decisions: outcomes are missing within the horizon. Check the join key, the horizon, and that failures are recorded. If only successes are ever recorded, use --absent-means-default.
  • "skipped" in the import summary: for some model calls the trace can't tell which tool ran. Instrument tool execution (execute_tool spans) or log with ao.span_attributes.
